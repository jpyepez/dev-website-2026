# Issue tracker: GitHub

Issues and specs for this repo live as GitHub issues. Use the `gh` CLI for all operations.

## Conventions

- **Create an issue**: `gh issue create --title "..." --body "..."`. Use a heredoc for multi-line bodies.
- **Read an issue**: `gh issue view <number> --json number,title,body,labels,comments`.
- **List issues**: `gh issue list --state open --json number,title,body,labels,comments --jq '[.[] | {number, title, body, labels: [.labels[].name], comments: [.comments[].body]}]'` with appropriate `--label` and `--state` filters.
- **Edit an issue body**: write the whole new body to a file, then `gh issue edit <number> --body-file <file>`. Never pass `-` or an empty body.
- **Comment on an issue**: `gh issue comment <number> --body "..."`
- **Apply / remove labels**: `gh issue edit <number> --add-label "..."` / `--remove-label "..."`
- **Close**: see "When a skill says close or resolve a ticket" below.

Infer the repo from `git remote -v`; `gh` does this automatically when run inside a clone.

## Pull requests as a triage surface

**PRs as a request surface: no.** _(Set to `yes` if this repo treats external PRs as feature requests; `/triage-issues` reads this flag.)_

When set to `yes`, PRs run through the same labels and states as issues, using the `gh pr` equivalents:

- **Read a PR**: `gh pr view <number> --comments` and `gh pr diff <number>` for the diff.
- **List external PRs for triage**: `gh pr list --state open --json number,title,body,labels,author,authorAssociation,comments` then keep only `authorAssociation` of `CONTRIBUTOR`, `FIRST_TIME_CONTRIBUTOR`, or `NONE` (drop `OWNER`/`MEMBER`/`COLLABORATOR`).
- **Comment / label / close**: `gh pr comment`, `gh pr edit --add-label`/`--remove-label`, `gh pr close`.

GitHub shares one number space across issues and PRs, so a bare `#42` may be either: resolve with `gh pr view 42` and fall back to `gh issue view 42`.

## When a skill says "publish to the issue tracker"

Create a GitHub issue.

## When a skill says "fetch the relevant ticket"

Read it as in **Read an issue** above.

## When a skill says "close" or "resolve" a ticket

A merged PR closes the ticket. Open a PR to `main` with `Closes #<n>` in the description for each ticket it finishes; the issue stays open until that PR merges, even when the work is finished on a branch.

Put each `Closes #<n>` on a line of its own, and write any other issue as "issue 50", without the `#`. GitHub reads `close`, `fix` or `resolve` in any tense before `#<n>`, anywhere in the description, as closing that issue: the board moves it to In progress at once, and the merge closes it.

Work that ships no code (wontfix, duplicates, pathfinder resolves, a parent spec whose sub-issues are all closed) closes directly: `gh issue close <number> --comment "..."`.

## Automation

The Triage workflow (`.github/workflows/triage.yml`) runs Claude on an issue, following `.github/prompts/triage.md`. It uses the same labels, [`ready` bar](triage-labels.md#the-ready-bar) and board Status as `/triage-issues`.

- **Triggers**: an issue being opened, or a manual run: `gh workflow run triage.yml -f issue=<n>`. Both only run from the workflow file on `main`, and only when the owner is the one acting. Editing or commenting on an issue doesn't re-run it: dispatch by hand.
- **Skips**: closed issues; issues not opened by the owner; issues labelled `notes`, `spec` or `pathfinder:*`; and, on opening only, issues that already carry an outcome label (`ready`, `needs-info`, `ready-for-human`, `wontfix`), such as a ticket a session files as `ready`. A manual run still re-triages those. A skipped run changes nothing.
- **Outcomes**: one category and one outcome label, with `needs-triage` removed, plus a comment giving the reasons point by point against the `ready` bar. For `ready`, it promotes a spec into the body and keeps the original as an `Original note:` comment. It recommends `wontfix` but never closes an issue, and never changes code, commits or pushes. Everything it writes starts with `> *This was generated by AI during triage.*`.
- **Outcome check**: before the agent, a step records the issue's newest comment id. After the agent, `bun run triage-outcome <n> <id>` (`scripts/triage-outcome.ts`) fails the run unless the issue has exactly one category and exactly one outcome other than `needs-triage`, **and** this run posted a triage comment: one newer than the recorded id, by the owner, starting with the disclaimer line, and not an `Original note:` comment. Labels alone can't show the run did its work, since on a re-triage the earlier run's labels already pass. A failed check names the rule that failed and leaves the board Status alone. A passing one sets the Status, as in the Board table under Repo conventions: Ready for `ready` (left alone if the issue is assigned), HITL for the rest.
- **Secrets**: `CLAUDE_CODE_OAUTH_TOKEN` signs Claude in, on the owner's plan. `OWNER_PAT` is the owner's token, used for `gh` and the action. `GITHUB_TOKEN` won't do: it can't edit the user-owned board, and labels it applies don't start other workflows, such as Implement. Both workflows use these two.
- **Caps**: 30 agent turns and 30 minutes per run, one run per issue at a time.

The Implement workflow (`.github/workflows/implement.yml`) runs Claude to build an issue, following `.github/prompts/implement.md`, and opens a PR that closes it. Nothing merges automatically.

- **Triggers**: the `ready` label being applied by the owner, or by Triage acting as the owner, or a manual run: `gh workflow run implement.yml -f issue=<n>`. Add `--ref <branch>` to run a branch's version of the workflow. Only the owner's actions start a run. Re-adding `ready` to an issue that has it creates no label event, so re-triaging a `ready` issue doesn't start a second build.
- **Skips**: read when the run starts, since it may have queued: closed issues, issues not opened by the owner, issues no longer labelled `ready`, and spec parents (labelled `spec`, or with sub-issues). A skipped run changes nothing.
- **Claim**: before the agent starts, a shell step assigns the issue to the owner and sets Status to In progress.
- **Build**: the agent rechecks the [`ready` bar](triage-labels.md#the-ready-bar), builds on `auto/issue-<n>` from `main` (or carries on from that branch and its draft PR, on a retry), gets lint, typecheck, tests, the build and the e2e suite green, walks the site on the [headless route](../browser-verification.md#headless-route), and opens a PR with `Closes #<n>`, a short test plan and, for a visible change, a screenshot comment. It never merges, edits labels or sets Status.
- **Hand-back**: the agent stops as soon as the ticket fails the `ready` bar or the change needs anything on the [hand-back list](#hand-back-list), and opens a draft PR saying why (`Part of issue <n>`). Any run that doesn't end in a ready-for-review PR (the agent gave up, ran out of turns or time, or crashed) ends with a shell step: a draft PR if there is a branch, a comment linking the run if there isn't, then `ready` swapped for `ready-for-human` and Status set to HITL. Relabel it `ready` to retry.
- **Secrets**: as for Triage. `OWNER_PAT` has no `workflow` scope (scopes `repo`, `project`, `read:org`), so the agent can't push changes to workflow files.
- **Caps**: 80 agent turns, 100 minutes for the agent and 120 for the job; one run at a time across all issues.

## Commit references

Reference the issue as `#<number>` in the commit message (e.g. `Closes #42` on the final commit).

## Repo conventions

- **Labels**: the triage roles use the strings in `triage-labels.md`. A closed issue is done; there is no `done` label.
- **A spec is a parent issue.** The issue body is the spec, labelled `ready` and `spec`. Its tickets are GitHub sub-issues of it, added in dependency order (blockers first): `gh api --method POST repos/<owner>/<repo>/issues/<parent>/sub_issues -F sub_issue_id=<child-db-id>`, where `<child-db-id>` is the child's numeric database id (`gh api repos/<owner>/<repo>/issues/<n> --jq .id`). Blocking between tickets uses native issue dependencies, as described under Wayfinding below.
- **Promote, don't duplicate.** When a spec comes out of an existing issue (usually an inbox item after triage), replace that issue's body with the spec instead of opening a new issue. First post the original body as a comment headed `Original note:` so it stays readable. Retitle the issue if the scope changed.
- **PRs close tickets**: see "When a skill says close or resolve a ticket" above.
- **Claim before working**: before implementing an issue, assign it with `gh issue edit <n> --add-assignee @me` and set its board Status to In progress (below).
- **Board**: the [dev-website-2026 project](https://github.com/users/jpyepez/projects/1) is one board with a column per Status: Inbox, Ready, In progress, HITL, Done. GitHub's built-in workflows add new issues to Inbox and move closed issues to Done. Keep Status in step with the triage label whenever you change one:

  | Change | Status |
  | --- | --- |
  | `needs-triage` applied | Inbox |
  | `needs-info`, `ready-for-human` or `wontfix` applied | HITL |
  | `ready` applied | Ready |
  | Issue claimed | In progress |
  | Work an agent handed back | HITL |

  HITL is everything waiting on the owner: questions to answer, work to build by hand, a `wontfix` to confirm and close, and work an agent handed back. Ready holds only what an agent may build (see [the `ready` bar](triage-labels.md#the-ready-bar)).

  Set it with `bun run board-status <n> <column>`, e.g. `bun run board-status 29 In progress`. The script adds the issue to the board if it isn't there, looks the column up by name (case doesn't matter) and fails, listing the valid names, if the board has no such column.
- **Not issues**: glossary, ADRs and out-of-scope records stay as files (see `domain.md`).

## Wayfinding operations

Used by `/pathfinder`. The **map** is a single issue with **child** issues as tickets. Issues labelled `pathfinder:*` are planning, not requests: `/triage-issues` skips them.

- **Map**: a single issue labelled `pathfinder:map`, holding the Notes / Decisions-so-far / Fog body. `gh issue create --label pathfinder:map`.
- **Child ticket**: an issue linked to the map as a GitHub sub-issue (`gh api` on the sub-issues endpoint). Where sub-issues aren't enabled, add the child to a task list in the map body and put `Part of #<map>` at the top of the child body. Labels: `pathfinder:<type>` (`research`/`prototype`/`grilling`/`task`). Once claimed, the ticket is assigned to the driving dev.
- **Blocking**: GitHub's **native issue dependencies**, the canonical, UI-visible representation. Add an edge with `gh api --method POST repos/<owner>/<repo>/issues/<child>/dependencies/blocked_by -F issue_id=<blocker-db-id>`, where `<blocker-db-id>` is the blocker's numeric **database id** (`gh api repos/<owner>/<repo>/issues/<n> --jq .id`, _not_ the `#number` or `node_id`). GitHub reports `issue_dependencies_summary.blocked_by` (open blockers only, the live gate). Where dependencies aren't available, fall back to a `Blocked by: #<n>, #<n>` line at the top of the child body. A ticket is unblocked when every blocker is closed.
- **Frontier query**: list the map's open children (`gh issue list --state open`, scoped to the map's sub-issues / task list), drop any with an open blocker (`issue_dependencies_summary.blocked_by > 0`, or an open issue in the `Blocked by` line) or an assignee; first in map order wins.
- **Claim**: `gh issue edit <n> --add-assignee @me`, the session's first write.
- **Resolve**: `gh issue comment <n> --body "<answer>"`, then `gh issue close <n>`, then append a context pointer (gist + link) to the map's Decisions-so-far.
